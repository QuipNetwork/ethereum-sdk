# SHRINCS wallet + paymaster e2e integration tests

End-to-end ERC-4337 flows where a **single** `UserOperation` is co-validated by both a `ShrincsWallet`
(its `validateUserOp` approval) and a `ShrincsPaymaster` (its sponsorship), run through the **real
v0.7 EntryPoint** on a Base Sepolia fork.

## Fork-gated

These tests `vm.createSelectFork(API_URL_BASE_SEPOLIA)` to get the canonical EntryPoint at
`0x0000000071727De22E5E9d8BAf0edAc6f37da032`, then `vm.chainid(31337)` so the live `getUserOpHash`
and both SHRINCS domain separators reproduce the values the vectors were signed under. They require
`API_URL_BASE_SEPOLIA` (in `.env`) and **do not run in a no-network lane** — same as the WOTS+
`test/integration/` suite.

The one exception is `encodingCrossCheck.t.sol`, which is **fork-free**: it validates the Rust
generator's hand-rolled `abi.encode(PublicKey, StatefulSignature)` and the canonical userOpHash purely
in Solidity, so it runs anywhere and fails fast if the encoding drifts.

```
forge test --match-path 'test/integration/shrincs/*'        # full suite (needs the fork RPC)
forge test --match-contract ShrincsE2E_encodingCrossCheck   # no RPC needed
```


### Why these vectors are special (the signing order)

Unlike the per-contract unit vectors, the wallet here signs the **real** EntryPoint userOpHash, which
commits to `keccak(paymasterAndData)` — so the two signatures are produced in a strict order:

1. The **paymaster** signs its `_userOpBindingHash` (which excludes `paymasterAndData[64:]`).
2. That signature is `abi.encode`d and embedded as `paymasterAndData[64:]`.
3. The canonical v0.7 `userOpHash` is computed over the now-complete `paymasterAndData`.
4. The **wallet** signs `erc4337PayloadHash(userOpHash, fee)`.

Reproducing step 3 requires rebuilding the exact on-chain `paymasterAndData` bytes, so the generator
**hand-rolls** `abi.encode(PublicKey, StatefulSignature)` (no extra Rust deps). Each case carries
`callData`, `paymasterAndData`, and `userOpHash` so the Solidity side can assert byte-exact agreement
(`encodingCrossCheck` locally, and `getUserOpHash(op) == userOpHash` against the live EntryPoint in
every assembled op).

### Fixed constants (generator ↔ `ShrincsE2EAssembler`)

- chainId `31337`; EntryPoint `0x0000…32`; `maxSignatures` 8; `executeFee` 0
- wallet `0x5B38Da6a701c568545dCfcB03FcB875f56beddC4`; paymaster
  `0xAb8483F64d9C6d1EcF9b849Ae677dD3315835cb2` (distinct — each binds its own address)
- recipient `0x…b0b0` (EOA), call target `0x…cA11` (etched `MockCallTarget`)
- shared `gas` block (generous verification gas — SPHINCS verify is heavy) baked into every userOpHash

## Cases → tests

| Case | Flow | Test file |
|---|---|---|
| `sponsoredEthTransfer` / `sponsoredContractCall` | sponsored happy path (ETH + contract call), events | `sponsoredExecute.t.sol` |
| `outOfOrderA` / `outOfOrderB` | leaves consumed out of numeric order (nonces sequential) | `multiOpOutOfOrder.t.sol` |
| `staleWalletLeafReplay` | consumed wallet leaf rejected under a fresh nonce → `AA24` | `multiOpOutOfOrder.t.sol` |
| `badPaymasterContext` | paymaster sig over a bad binding → `AA34` | `rejections.t.sol` |
| `windowNotDue` / `windowExpired` | absolute validity bounds → `AA32` | `rejections.t.sol` |
| (op.signature byte-flip, no vector) | invalid wallet sig → `AA24` | `rejections.t.sol` |
| `paymasterRotationNewKey` (+ `verifierKey2`) | paymaster verifier rotation: new key accepted, old rejected, fresh namespace | `keyRotation.t.sol` |
| `walletRotateKey` | real owner `rotateKey` bumps the wallet epoch; old-epoch sponsorship rejected → `AA24` | `keyRotation.t.sol` |
